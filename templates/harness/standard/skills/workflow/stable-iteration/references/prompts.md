# Stable Iteration — Prompt 模板

> 使用时将 `{占位符}` 替换为实际路径与函数名；通过 `@file` 引用文件，避免整库粘贴。

---

## Step 1

```
@{target_dir}

你是代码审查专家。请依次完成：

1. 列出所有超过 50 行的函数，标注行号和文件
2. 找出重复代码片段（3 行以上相同或高度相似），标注位置
3. 识别未使用的 import 和导出的接口
4. 标注所有 try-catch 吞异常的情况
5. 按优先级排序，只返回 Top 10 问题

格式：[P0/P1/P2] 文件:行号 → 问题描述 → 修改方向

不要给出完整代码，只输出诊断报告。
```

---

## Step 2

```
@{target_file}

梳理该文件的所有依赖关系：

1. 直接导入：列出所有 import 及来源
2. 间接依赖：追踪 import 至少深入两层
3. 外部输入：环境变量、配置文件路径、数据库表名
4. 副作用：对外部状态的写操作（缓存、日志、MQ 等）
5. 条件触发依赖：用注释标注触发条件

输出依赖树，根节点为 {target_file}。
最后单独列出「保护区」：被多模块引用或跨团队维护的依赖。
```

---

## Step 3

```
@{target_file}::{function_name}

需要重构函数 {function_name}（当前约 {line_count} 行）。

约束：
1. 保持现有 public API 签名不变（参数类型、返回值）
2. 提取公共逻辑为私有辅助函数，每个新函数 ≤40 行
3. 保留原有错误处理模式
4. 不改变任何外部可观察行为（日志、异常类型、HTTP 状态码）
5. 不更换内部数据结构，除非我明确要求

请先输出重构计划，等我确认后再生成代码。计划格式：
- 拆分为哪些新函数
- 每个新函数职责（一句话）
- 需关注的边界情况
```

---

## Step 4

```
@{target_file}::{function_name}

在修改实现之前，先为 {function_name} 编写完整单元测试。

函数信息：
- 文件：{target_file}
- 函数：{function_name}
- 主要逻辑：{brief_description}

测试要求：
1. 覆盖所有已知分支
2. 包含边界值与 null/空值场景
3. 每条测试名描述输入与期望输出
4. 使用项目已有测试框架（{test_framework}）
5. 先输出测试代码，不要修改原函数

等我确认测试通过后，再修改实现；测试失败时将错误信息反馈给你修复。
```

---

## Step 5

```
@diff

假设你是第一次接触本项目的新人工程师，正在 review 这份 PR。
你没有历史背景，也没有读过设计文档。

请从以下角度审查：
1. 可读性：5 分钟内能否理解在做什么？哪里困惑？
2. 正确性：有没有不对劲的逻辑？标注行号
3. 一致性：与项目现有代码风格是否一致？
4. 安全性：注入、信息泄露、未处理异常？
5. 性能：循环内查库、不必要序列化？

每个问题给出行号与具体担忧，不要泛泛而谈。
```
