# 阶段 6 — 独立反证审计

角色：代码审计员。尽可能使用不同 Agent/新会话；不得仅相信撰写者的总结。输入 `.harness/wiki/` 全部文档与源码。

输出：`.harness/wiki/_audit.md`

审计策略：
1. 从业务规则、状态机、数据模型、权限、金额/计数计算、事务/幂等、跨域时序中抽样至少 20 条；仓库小于 20 条时全部检查。样本应覆盖至少 3 个领域（若项目确有 3 个以上领域），并包含高风险结论。
2. 抽样应可复现：记录抽样方法、样本总数、审计 commit、执行日期。优先随机/分层抽样，不只检查最容易验证的结论。
3. 每条回到源码重新定位路径与行号，不沿用文档中已经给出的解释。
4. 检查：证据是否存在；行号是否准确；代码是否真的支持结论；是否忽略条件/例外/错误路径；是否有反例；是否把测试/注释误当生产行为；图表是否虚构时序；状态机是否漏状态；DDL 与模型是否冲突。
5. 检查覆盖性：路由数量核对、非 HTTP 入口覆盖、文件链接、ER 关系、pending 汇总、文档 commit 与当前源码是否一致。
6. 发现错误时给出修正建议；协调 Agent 修正文档后，审计员**必须重新检查修订项**（写入「已修订项复核」）。不得只写“建议注意”而不指出具体错误。
7. 结束时更新 `_manifest.yaml` 的 `audit_status`（`passed` / `conditional` / `failed`）与 `pending_count`。

输出格式：
# Audit metadata
- commit / 日期 / 审计者 / 样本策略 / 总样本数
## 结论摘要
## 逐条核验
| ID | 文档位置 | 被审计结论 | 独立源码证据 | 判定（通过/部分支持/错误/无法验证） | 问题与修正建议 |
## 覆盖性检查
## 已修订项复核
## 剩余风险与阻塞
## 最终结论（通过/有条件通过/不通过）

判定标准：
- 通过：证据位置正确且足以支持结论。
- 部分支持：核心方向可能正确但条件/边界遗漏。
- 错误：证据不支持或与实现矛盾。
- 无法验证：证据在仓库范围内不可访问，不得当作通过。

不得为达到 100% 通过率而删除错误样本或降低标准。结束时更新 `STATUS.md`。
