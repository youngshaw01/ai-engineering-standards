# 阶段 6 — 独立反证审计

角色：代码审计员。尽可能使用不同 Agent/新会话；不得仅相信撰写者的总结。输入 `.harness/wiki/` 全部文档与源码。

输出：`.harness/wiki/_audit.md`

审计策略：
1. 从业务规则、状态机、数据模型、权限、金额/计数计算、事务/幂等、跨域时序中抽样至少 20 条；仓库小于 20 条时全部检查。样本应覆盖至少 3 个领域（若项目确有 3 个以上领域），并包含高风险结论。
2. 抽样应可复现：记录抽样方法、样本总数、审计 commit、执行日期。优先随机/分层抽样，不只检查最容易验证的结论。
3. 每条回到源码重新定位路径与行号，不沿用文档中已经给出的解释。
4. 检查：证据是否存在；行号是否准确；代码是否真的支持结论；是否忽略条件/例外/错误路径；是否有反例；是否把测试/注释误当生产行为；图表是否虚构时序；状态机是否漏状态；DDL 与模型是否冲突。
5. 检查覆盖性：路由数量核对、非 HTTP 入口覆盖、文件链接、ER 关系、pending 汇总、文档 commit 与当前源码是否一致。
6. 发现错误时给出修正建议；协调 Agent 修正文档后，审计员**必须重新检查修订项**（写入「已修订项复核」）。不得只写“建议注意”而不指出具体错误。
7. 声明**口径时点**：所有统计数字标注审计执行的基线时点；若审计后追加或修改了 wiki 内容（如补写索引附录），必须声明追加/修改的文件、行数与字节数，以及统计是否重算及原因；同时声明未纳入统计的范围（行内 `[待确认]` 标注数量、非同源引用、未覆盖目录等）。
8. 逐条核对 Skill 的「反模式」与「完成检查清单」，给出 ✅ / ⚠️ / ❌ 与清单结果统计；修正建议按 P0（需用户决策或运行验证）/ P1（本任务内可补）/ P2（暂不处理）分级；并明写本次审计**无法验证**的范围（审计局限）。
9. 审计报告**自身**不得留有未修正的 ❌；必须由用户决策的项写「需用户确认」。
10. 结束时更新 `_manifest.yaml` 的 `audit_status`（`passed` / `conditional` / `failed`）与 `pending_count`。

输出格式（章节顺序对齐 `_audit.template.md`）：
# Audit metadata
- revision/commit / 日期 / 审计者 / 样本策略 / 总样本数
## 一、审计方法与可复现口径（含口径声明：基线时点、审计后追加量、未纳入统计范围）
## 二、量化结果（规模 / 锚点解析 / 标注与图表）
## 三、覆盖度核对（能力地图自洽性 / 模板合规 / 产物完整性 / 反查表抽样）
## 四、审计发现（AUD-01…，逐条标 🟢 / 🟡 / 🔴，已修复项标「已修复」）
## 五、抽样人工回溯记录
| # | 文档位置 | 被审计结论 | 独立源码证据 | 判定（通过/部分支持/错误/无法验证） | 备注 |
## 六、反模式核对
## 七、完成检查清单核对（含 ✅ / ⚠️ / ❌ 统计）
## 八、修正建议（P0 / P1 / P2）
## 九、审计局限
## 最终结论（通过/有条件通过/不通过）

判定标准：
- 通过：证据位置正确且足以支持结论。
- 部分支持：核心方向可能正确但条件/边界遗漏。
- 错误：证据不支持或与实现矛盾。
- 无法验证：证据在仓库范围内不可访问，不得当作通过。

不得为达到 100% 通过率而删除错误样本或降低标准。结束时更新 `STATUS.md`。
