# Bootstrap：存量项目初始知识梳理工作包

> 标准库（Layer 0）资产：Prompt 与规程在**标准库内读取，不复制进消费项目**（红线 1）。  
> 真正的知识文档必须由有仓库访问权限的 Agent 根据实际源码生成：AI 辅助梳理 + **人工审定**。

## 何时使用

- 存量项目接入 v3 后，需要根据业务代码建立 `docs/knowledge/` 初始集（架构、领域模块、DB/ER、部署、术语）。
- 对已有旧文档的项目：定位为"**校验现有文档与代码一致性 + 补缺口**"，非从零重写。
- 新项目（无存量代码）不需要本流水线。

## 启动方式

1. 确认目标项目已接入 v3（`validate` 无 error）。
2. 创建变更单元 `.harness/workspace/changes/docs-knowledge-bootstrap-{NNN}/`。
3. 将标准库 `prompts/COORDINATOR.md` 交给有仓库权限的 Agent，要求从**阶段 0**开始执行。
   - **不要**让它直接跳到阶段 3 或一次性生成全部文档。
4. 每个阶段验收通过后再继续；完成后人工审定 `docs/knowledge/_audit.md` 与产物质量。

## 包含内容

| 路径 | 用途 |
|------|------|
| `prompts/` | 阶段 0–6 Prompt + `07-finalize.md`（交付收尾）+ `COORDINATOR.md` |
| `workflow/` | 操作手册、质量门槛、交接协议、验证清单、状态模板 |
| `artifacts/` | knowledge 索引、`_manifest.yaml`、`_pending` / `_audit` 模板 |

主流程为**阶段 0→6**；`07-finalize.md` 为阶段 6 后的交付收尾，不占独立阶段编号。协调 Agent 控制阶段推进；每个业务域独立分析；每阶段有明确输入、输出和验收门槛。

## 不可违反的规则（沿袭 v1 封板，落位已 v3 化）

1. 默认只读源码。未经用户明确授权，不修改业务代码、数据库、部署文件、依赖版本或运行环境；本工作只允许创建/修改 `docs/knowledge/` 与 bootstrap 变更单元目录内的文档。
2. 不编造。每个重要事实、业务规则、状态转换、表关系和外部调用都必须有证据锚点：`相对路径:起始行-结束行`。
3. 证据分级统一使用 `[事实]`、`[推断]`、`[待确认]`。事实必须直接由代码/配置/DDL/测试支持；推断必须解释依据与不确定性；无证据结论只能列入待确认。
4. 按业务能力/业务域组织文档，不按 Controller/Service/DAO 等技术分层组织；技术架构作为横切文档记录。
5. 不把目录名、类名、注释、API 名称单独当成业务事实；必须沿调用链验证到持久化、消息、外部调用或响应。
6. 不默认项目使用某种语言、框架、数据库、MQ、业务域或部署方式。先侦察，再决定分析方法。
7. 不声称"全量"除非做了可复现的扫描与数量校验。记录扫描命令、纳入/排除规则、生成时间、源码基线标识（Git commit SHA 或 SVN revision）。
8. 对动态路由、反射注册、代码生成、插件、运行时配置、外部仓库或不可访问依赖，要明确记录覆盖限制。
9. 禁止为了填满模板而写空洞内容。没有对应机制时写"在已检查范围内未发现"，并列出检查范围；不能据此断言全项目不存在。
10. 每阶段必须先检查输入和输出；未通过验收不得宣告完成。修订应保留审计可追溯性。
11. 不执行破坏性命令、生产操作、真实拨号/支付/发信、迁移、压测或联网外呼；不输出秘密值。配置只记录键名、用途、来源，凭据写为 `[REDACTED]`。
12. 不要将整个项目一次性塞入单个上下文。采用阶段化工作、领域白名单、短而明确的交接记录。

## 推荐首次执行节奏

先用本流程完成一次**全局 Recon + 业务能力地图**（阶段 0–2），确认入口盘点可靠后，再逐域深入（阶段 3+）。这样最容易发现流程本身的问题，也能避免一开始就把大量未经验证的内容写进知识库。
