# Legacy Project Wiki — Prompt 模板

> 每阶段**开新会话**执行；将上一阶段产物文件作为输入喂入。
> 占位符 `{...}` 使用时替换为实际路径 / 名域，避免整库粘贴。

---

## Phase 0 — 准备

```
本次任务：对 {项目名} 做遗留系统业务梳理，产出写入 .harness/wiki/。

范围确认（请逐条回答后再继续）：
1. 分析范围：{全仓库 | 指定子模块 | 指定目录}
2. 是否包含：{后端 / 前端 / 定时任务 / 运维脚本}
3. 技术栈初判：{语言 + 框架}

约束：本阶段只创建目录骨架，不读业务代码。
```

---

## Phase 1 — 全局侦察（Recon）

```
角色：遗留系统分析专家。

任务：对当前仓库做只读侦察，产出「事实清单」。本阶段禁止写业务文档。

硬性约束：
- 只读操作，禁止修改任何源码
- 每条结论必须附 `文件路径:行号` 作为证据
- 不确定的内容标注 [待确认]，禁止编造或推测业务含义
- 不做"该模块负责 XX 业务"这类主观描述

请依次执行并输出：

1. 技术栈识别
   - 语言及版本、框架、ORM、DB、缓存、MQ、调度器
   - 依据文件：pom.xml / package.json / go.mod / requirements.txt 等

2. 目录结构（深度 2）
   - 树形列出，每个目录只标注"推测职责"，加 [待确认]

3. 入口点清单（后续所有分析的起点）
   - HTTP 路由注册文件 → 列出所有路由前缀
   - 定时任务（cron / @Scheduled / celery beat）
   - 消息消费者（MQ listener / consumer）
   - CLI / main 函数
   - 启动脚本

4. 配置与环境变量
   - 配置文件路径、关键配置项（DB、第三方服务、开关）

5. 规模与热点
   - 代码行数 Top 20 文件
   - 通过配置 / SDK 调用推断出的第三方服务清单

输出写入：.harness/wiki/00-recon.md
```

**验收**：随便抽 3 条结论，能顺着 `文件:行号` 找到证据。

## Phase 2 — 业务能力提取（Clustering）

```
输入：.harness/wiki/00-recon.md

任务：提取业务能力清单。

方法（必须严格执行）：
1. 读取所有路由 / API 定义文件，逐条列出 endpoint（method + path + handler 函数）
2. 按 URL 前缀 + 语义聚类，归并为「业务能力」
   ⚠️ 这是业务聚类，不是技术分层。例如 /api/v1/user/login 和
   /api/v1/user/register 属于「用户认证」能力，不是"user 模块"。
3. 每个业务能力给出：名称、一句话说明、包含的 endpoint、入口文件

输出表格到：.harness/wiki/01-capability-map.md

| 能力域 | 说明 | 主要 endpoint | 入口文件:行号 |
|---|---|---|---|

硬性要求：
- 不得遗漏任何一个 endpoint（最后附总数校验：扫描到 N 个，归类 M 个）
- 无法归类的放进「未分类」，并说明为什么无法归类
- 每条 endpoint 必须能点击跳到代码位置

最后：列出你认为需要深入分析的 Top 10 能力域（按 endpoint 数量 + 业务重要性排序）。
```

**验收**：endpoint 总数 = 归类数，无遗漏。

## Phase 3 — 领域深度分析（逐域，可并行）

```
输入：
- .harness/wiki/00-recon.md
- .harness/wiki/01-capability-map.md

任务：深度分析业务域【{domain}】。

执行步骤（严格按顺序）：
1. 从该域的入口路由开始，顺着调用链往下读代码，
   直到数据落库 / 外部调用 / 返回响应。不要跳读。
2. 画出端到端调用链，粒度到 `文件:函数名`
3. 抽取数据模型：表名、关键字段、索引、关联关系
4. 抽取业务规则：校验逻辑、状态流转、金额计算、权限判断
5. 抽取外部依赖：其他服务、第三方 API、MQ topic、缓存 key
6. 识别特殊逻辑：TODO/FIXME、魔法数字、硬编码、绕过逻辑、兼容代码

输出到：.harness/wiki/domains/{domain}.md

模板（必须遵守）：
## 1. 概述（3 句话内）
## 2. 端到端流程
   （mermaid sequenceDiagram，标注 文件:函数）
## 3. 数据模型
   （表结构 + ER 关系，标注建表 SQL 位置）
## 4. 业务规则
   （每条规则一行，附 文件:行号）
## 5. 状态机
   （mermaid stateDiagram）
## 6. 外部依赖
## 7. 已知坑 / 特殊逻辑
## 8. 待确认问题
   （每条写：疑问 + 已查证范围 + 需要谁确认）

硬性约束：
- 每条业务规则必须有代码位置
- 推断内容标 [推断]，并说明推断依据
- 找不到证据的写进第 8 节，不要编造
```

**并行技巧**：把 Top 10 能力域分发给子 agent，每个子 agent 只读自己域相关文件（在 prompt 里给出**文件白名单**），能大幅节省上下文。

## Phase 4 — 横切关注点

```
输入：00-recon.md、01-capability-map.md、domains/*.md

任务：梳理横切关注点，产出 02-architecture.md。

覆盖：
1. 认证与授权：登录态怎么存、token 怎么校验、权限模型（RBAC/ABAC）
2. 错误处理：统一异常处理、错误码体系
3. 事务边界：@Transactional 分布、分布式事务方案
4. 缓存策略：key 命名、失效时机、穿透/雪崩防护
5. 日志与监控：traceId 传递、关键埋点
6. 配置与开关：feature flag、灰度
7. 部署拓扑：从 Dockerfile / k8s yaml / CI 脚本推断

每条结论附代码位置。推断内容标 [推断]。

同时产出：
- data/er.md：汇总所有领域的表，画全局 ER 图
- data/state-machines.md：汇总所有状态机
- flows/*.md：跨域流程（如"下单→支付→发货"跨越 3 个域）
```

## Phase 5 — 索引与交叉链接

```
输入：.harness/wiki/ 下所有文件

任务：生成 README.md 索引，要求：
1. 按「新人上手路径」排序阅读顺序
2. 每个文件一句话摘要
3. 维护「业务域 → 代码路径」反查表
4. 汇总所有 [待确认] 到根目录 _pending.md
5. 检查交叉引用：每个 domains/*.md 里提到的其他域，
   必须链接到对应文件（markdown 相对链接）
6. 找出孤立文件（没被任何文件引用的）并报告
```

## Phase 6 — 审计校验（防幻觉）

```
角色：代码审计员，你的任务是"找茬"。

输入：.harness/wiki/ 全部文档 + 源码仓库

任务：随机抽取 20 条文档结论（优先抽业务规则、状态机、数据模型），
逐条回到源码验证：
- 证据是否真实存在（文件:行号 是否对得上）
- 结论是否被代码支持（还是过度推断）
- 是否有遗漏的反例（代码里有但文档没写）

输出：.harness/wiki/_audit.md

格式：
| 文档位置 | 结论 | 证据核对 | 判定 |
|---|---|---|---|
| domains/order.md:45 | 订单超时30分钟取消 | OrderJob.java:88 ✅ | 通过 |
| domains/order.md:52 | 支付后不可取消 | 未找到校验，PaymentService 无判断 | ❌ 错误 |

对判定为错误的，直接给出修正建议。
```

把 `_audit.md` 的修正反馈给 Phase 3 的 agent，让它修订。
