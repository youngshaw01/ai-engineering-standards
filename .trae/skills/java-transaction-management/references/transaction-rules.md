# 事务规则（TX）v1.0

> 版本 1.0 · 2026-10-30 · 冻结于评审修订后 · 母版，项目覆盖层可覆盖

## 适用范围与级别

### 模块识别

审核开始前必须先判定对象所属模块，模块代号：`svc`=acquire-service、`dao`=acquire-dao、`ctl`=controller、`lsn`=listener/event。

| 审核对象 | 模块代号 | 判定依据 |
|---|---|---|
| `*ServiceImpl` / `*Service`（事务编排、迁移、状态流转） | svc | 模块 `acquire-service`，包名含 `service` |
| `*Dao` / `*DaoImpl` / Mapper（SQL 构造与更新条件） | dao | 模块 `acquire-dao` |
| `*Controller` / 请求入口类 | ctl | `acquire-manage` / `acquire-merchant` 的 controller 包 |
| `*Listener` / `@EventListener` / `@TransactionalEventListener` / `@Async` 事件处理方法 | lsn | 包名含 `listener`，或方法为事件处理入口 |

一次审核跨多个模块时（如 svc 调用 dao 与 lsn），按实际命中的模块分别启用规则，并在报告中按模块分组说明。

### 级别与启用

| ID | 适用模块 | 级别 |
|---|---|---|
| TX-01 | svc | 必检 |
| TX-02 | svc | 必检 |
| TX-03 | svc | 必检 |
| TX-04 | lsn, svc | 必检 |
| TX-05 | svc, dao | 必检 |
| TX-06 | dao | 必检 |
| TX-07 | svc, lsn, ctl | 必检 |
| TX-08 | svc, lsn | 必检 |
| TX-09 | svc | 选检 |
| TX-10 | svc | 选检 |

- 必检规则：范围内出现该模块即自动启用
- 选检规则：默认不启用，需在范围声明中显式点名，或由 `java-code-review` 汇总阶段决定启用
- **报告首部必须逐条列出本次实际启用的 TX 规则 ID** 及未启用的选检规则；`svc` / `dao` / `lsn` 的规则不得混用

## TX-01 事务原子性边界必须明确

- 判定：能否从代码、调用链与业务约束中识别出「必须原子提交的操作集合」，以及回滚范围与提交后动作的划分
- 说明：注释、方法命名、事务配置均可作为辅助证据，**不要求以注释作为唯一证据**
- 反例：事务内包含多个业务迁移操作，但无法确认哪些必须共同成功或失败
- 正例：能明确指出原子操作集合、回滚范围与提交后动作（如「基础信息 + 结算账户 + 分支 + 人员 + 文件迁移必须原子；远程注册与事件在提交后」）

## TX-02 事务内禁远程调用

- 判定：事务块或 `@Transactional` 方法内是否存在 HTTP/RPC/MQ 发送
- 反例：事务内调用 Airwallex 注册接口，接口超时导致行锁长时间持有
- 正例：远程调用移到提交后，失败按 TX-08 的恢复语义处理

## TX-03 事务事件必须与事务结果一致

- 判定：事件发布时机与监听器执行阶段是否匹配业务一致性要求
- 反例：事务内发布事件，普通 `@EventListener` 立即执行副作用，随后数据库事务回滚，消费方看到不存在的数据
- 正例：事务内发布事件，由 `AFTER_COMMIT` 监听器在提交后执行；或通过事务同步机制确保副作用只在提交成功后触发
- 注意：**不能仅凭 `publishEvent` 位于事务内就判定违规**，关键在监听器的执行阶段与副作用类型

## TX-04 AFTER_COMMIT 监听器必须核实发布时机

- 判定：事件发布时是否存在活动事务，以及监听器的 `phase`、`fallbackExecution` 是否符合预期
- 说明：`fallbackExecution = true` 只表示「无活动事务时也执行」，**不能保证在数据库提交后执行，不能作为统一修复方案**
- 反例：业务要求提交后执行，但事件在事务外发布，监听器为 `AFTER_COMMIT` 且未设 `fallbackExecution`，导致监听器不执行（编程式事务提交后 `TransactionSynchronizationManager` 已清理）
- 正例：按发布场景明确选择「事务内发布 + AFTER_COMMIT」「事务外发布 + 普通监听器」或事务同步机制；仅当确实需要无事务时也执行，才启用 `fallbackExecution = true`
- 报告必须写明该事件是否可能**丢失、提前执行或重复执行**

## TX-05 影响行数按业务语义校验

- 判定：关键业务状态更新的返回值是否被检查，是否结合业务语义解释了 0 行的含义
- 说明：`0` 行可能代表并发冲突、状态不匹配或幂等重复，必须按业务语义判断；**允许零行的幂等操作需在代码或报告中明确说明**，不要求所有 UPDATE/DELETE 机械抛异常
- 反例：关键状态更新 `dao.updateXxx(id, dto);` 返回值被丢弃，失败与并发都无感知
- 正例：`int updated = ...; if (updated == 0) { 按语义处理：并发冲突抛 ERROR_DATA_CONCURRENT / 幂等重复直接返回 }`

## TX-06 状态变更的前置状态条件（CAS）

- 判定：存在并发竞争或状态迁移约束的状态更新，WHERE 是否包含期望的前置状态
- 说明：**不对所有状态更新机械要求前置条件**；纯字段回写、无状态机语义的更新不适用本规则
- 反例：`UPDATE ... SET mcht_state = ? WHERE mcht_id = ?`，配合事务外「读—判—写」校验，两个请求可同时通过
- 正例：`WHERE mcht_id = ? AND mcht_state = ?`（期望前置态），配合 TX-05 校验行数

## TX-07 异常不得吞没，须保留可诊断信息

- 判定：catch 后是否只记日志、是否包装丢失根因、是否把业务异常降级为通用异常
- 反例：`catch (Exception e) { throw BizException.of(FAILED, msg); }`，原始异常既未记录也未传递
- 正例：先 `log.error(msg, e)` 保留原始堆栈；业务异常原样抛出；非业务异常包装为对应错误码
- 说明：**不得为了保留 cause 而擅自改动项目异常体系**；若项目异常类型无 cause 重载，以日志保留堆栈即为合规

## TX-08 提交后动作必须具备失败恢复语义

- 判定：事务提交后的远程调用、事件或消息发送失败时，是否存在可追踪、可恢复的处理机制
- 正例：重试、幂等补偿、可靠消息、补偿记录或明确的待处理状态
- 反例：只记录日志，系统没有重试、补偿或人工处理入口
- 说明：**事务已提交，提交后抛异常不能回滚数据库**。报告必须区分「数据库提交结果」与「提交后动作结果」，不得把提交后异常描述为数据库事务回滚

## TX-09 幂等与重复提交保护

- 判定：重复执行同一业务动作时，是否有机制保证只产生一次副作用
- 说明：唯一键、幂等键、去重状态校验可以组合使用，**不要求每个场景同时具备三种机制**
- 反例：同一 mchtNo 重复复核会重复生成商户号/重复迁移
- 正例：以唯一业务键或状态条件保证只成功一次，并说明所选机制的有效边界

## TX-10 自调用导致事务失效

- 判定：同类内部方法调用是否实际绕过了事务代理，从而导致事务注解失效
- 说明：只检查**实际影响事务行为**的自调用；不因存在同类内部调用就判定违规
- 反例：`this.doInTx()` 调用带 `@Transactional` 的方法，事务不生效
- 正例：通过注入自身代理或拆分到独立 bean；无事务注解的纯计算私有方法自调用不算违规

## 规则间冲突与计数

1. TX-03 与 TX-04 针对同一段事件代码时，须分别陈述「事件与事务结果是否一致」与「发布时机与监听器配置是否匹配」，不得把同一违反事实重复计数
2. TX-05 与 TX-06 是配合关系：有前置状态条件而无行数校验，或反之，均不完整
3. 同一处代码命中多条规则时按规则分别记录，但同一违反事实只计一次
4. 本规则集只判断事务边界与一致性；代码结构由 `java-code-structure` 负责，最终由 `java-code-review` 汇总两者结果
