# 结构规则（ST）v1.0

> 版本 1.0 · 2026-10-30 · 冻结于评审修订后 · 母版，项目覆盖层可覆盖

## 适用范围与级别

### 模块识别

审核开始前必须先判定对象所属模块，模块代号：`svc`=acquire-service、`dao`=acquire-dao、`ctl`=controller、`lsn`=listener/event。

| 审核对象 | 模块代号 | 判定依据 |
|---|---|---|
| `*ServiceImpl` / `*Service`（业务服务） | svc | 模块 `acquire-service`，包名含 `service` |
| `*Dao` / `*DaoImpl` / Mapper | dao | 模块 `acquire-dao` |
| `*Controller` / 请求入口类 | ctl | `acquire-manage` / `acquire-merchant` 的 controller 包 |
| `*Listener` / `@EventListener` / `@TransactionalEventListener` / `@Async` 事件处理方法 | lsn | 包名含 `listener`，或方法为事件处理入口 |

一个文件同时包含多类对象时，按被审方法所在类的角色判定，并在报告中写明。

### 级别与启用

| ID | 适用模块 | 级别 |
|---|---|---|
| ST-01 | svc, ctl, lsn | 必检 |
| ST-02 | svc, ctl, lsn | 必检 |
| ST-03 | svc, ctl | 选检 |
| ST-04 | svc, ctl | 必检 |
| ST-05 | 全模块 | 选检 |
| ST-06 | svc, dao | 必检 |
| ST-07 | svc, lsn | 必检 |
| ST-08 | 全模块 | 选检 |
| ST-09 | 全模块 | 选检 |
| ST-10 | svc, dao | 选检 |

- 必检规则：只要范围内出现该模块即自动启用
- 选检规则：默认不启用，需在范围声明中显式点名，或由 `java-code-review` 汇总阶段决定启用
- **报告首部必须逐条列出本次实际启用的规则 ID**，以及未启用的选检规则，不得由执行者临时决定省略

## ST-01 单方法单抽象层

- 判定：一个方法内是否同时存在「流程编排」与「具体业务动作」两种抽象层级
- 反例：`recheck()` 内既有分支决策，又有 DAO 更新、角色升级、远程调用、事件发布
- 正例：入口方法只调用 `loadAndValidate` / `reject` / `approveInTransaction` / `postCommit`
- 常见误报：短方法内顺序调用多个同级私有方法属于正常编排
- 与 ST-04 的分工：ST-01 判「抽象层次是否混杂」，ST-04 判「入口是否承担过多实现细节」。两者可同时命中，但必须分别陈述各自的违反事实

## ST-02 方法长度与嵌套（触发规则）

- 判定：有效行 > 50 或嵌套 > 3 层（if/for/try 计一层）时，必须进一步检查职责、复杂度和可读性
- 说明：**超过阈值本身不构成违规**；短方法也不代表结构合理。本规则是检查触发器，不是违规标准
- 报告写法：命中 ST-02 时给出实测有效行数与最大嵌套层数；若要下违规结论，须落到 ST-01 / ST-04 / ST-08 等具体规则
- 反例：单方法 200 行以上，事务内再嵌 3 层判断，且同时命中 ST-01
- 正例：守卫式早返回把嵌套压到 ≤ 2

## ST-03 分支复杂度

- 判定：分支数量增加是否已导致决策逻辑复杂、重复或扩展困难（判断条件重复、状态值散落字符串、分支内大量复制粘贴）
- 说明：**不得仅因分支数量达到某个阈值就强制引入设计模式**；两个提前返回的业务结果属于正常分支结构
- 反例：`if ("2".equals(state)) ... else if ("3".equals(state)) ...` 在多个方法内重复出现，新增状态需改动多处
- 正例：状态以枚举表达，必要时按枚举映射分发
- 常见误报：`if (dto.isNoPass()) { reject(); return; }` 这类两个业务出口的早返回

## ST-04 入口方法编排化

- 判定：入口方法是否直接承载大量底层实现细节（直接写 SQL、逐表迁移、远程调用、事件发布、大段数据装配）
- 说明：入口方法应以业务流程编排为主，**允许根据业务需要包含校验、分支、委托与后置动作，具体结构不要求固定为四个阶段**
- 反例：入口方法中直接写 SQL、调远程、发事件
- 正例：每段委托给私有方法或独立组件，入口只做顺序编排
- 常见误报：入口按顺序调用多个同级私有方法；少量参数装配与结果封装

## ST-05 依赖方向

- 判定：service 是否反向依赖 controller/web 层；底层模块是否依赖上层模块
- 说明：必须以项目真实模块依赖为准，不预设结论
- 反例：`acquire-dao` 引用 `acquire-service` 的类
- 正例：controller → service → dao 单向
- 常见误报：同层模块间通过 bean 包共享 DTO（项目既有范式，不算反转）

## ST-06 查询方法无副作用

- 判定：命名含 get/list/query/find/count 的方法是否写库、发事件、调远程写接口
- 说明：方法命名只是检查入口，必须追踪方法体内实际调用链才能下结论
- 反例：`getMchtInfo()` 内部刷新状态并写库
- 正例：读方法只读；写操作由显式命名的方法承担
- 常见误报：方法名为 get 但语义上是「get-or-create」且在项目内已统一约定

## ST-07 外部依赖可替换

- 判定：影响业务决策、业务状态或测试结果的外部依赖，是否具备合理的替换或隔离能力
- 说明：**不要求所有外部依赖采用同一种注入形式**；纯日志时间戳、非关键诊断信息不要求注入
- 反例：方法内 `new RestTemplate().postForObject(...)`；`System.currentTimeMillis()` 直接参与业务状态判断且无法在测试中固定
- 正例：注入远程服务、`ApplicationEventPublisher`；业务时间通过 `Clock` 或可覆盖的时间组件获取
- 常见误报：日志中的时间戳；项目既有统一通信工具类的静态调用（属既有范式，需在覆盖层声明）

## ST-08 重复逻辑提取

- 判定：同一业务规则在 ≥ 3 处重复实现时，评估是否提取
- 说明：**只有语义一致、变化原因相同的逻辑才适合统一抽取**；形似但语义不同的代码不得合并
- 反例：三处重复 `if (state == null || !PENDING_RECHECK.equals(state)) throw ...`，且三处会因同一需求一起变化
- 正例：提取为常量或校验方法
- 常见误报：三处代码结构相似但分别属于不同业务规则

## ST-09 命名一致

- 判定：命名是否符合 `docs/rules/detail/java-conventions.md` 命名表
- 说明：本规则只做引用，不重复定义命名表

## ST-10 参数数量

- 判定：方法参数 > 4 个时触发检查，评估是否应收敛为请求对象
- 说明：参数数量是检查触发器，不是违规标准
- 反例：`registSettAccounts(mchtNo, acctUrl, token, userid, retry, timeout)`
- 正例：收敛为请求对象或上下文对象
- 常见误报：框架回调签名不可改时不算

## 规则间冲突与计数

1. ST-01 与 ST-04 可同时命中同一方法，报告必须分别说明「抽象层次混杂」与「入口承载实现细节」两个不同事实
2. 同一处代码命中多条规则时，按规则分别记录，但不得把同一违反事实重复计数为多个问题
3. ST-02 永远作为触发证据出现，不与 ST-01 / ST-04 并列计为独立违规
4. 本规则集只判断代码结构；事务可靠性、异常语义、并发一致性由 `java-transaction-management` 负责，最终由 `java-code-review` 汇总
